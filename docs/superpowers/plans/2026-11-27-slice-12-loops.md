# Loops Are Resources (slice 12) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A loop is a manifest the workbench lists, runs, copies, edits, exports and imports. Today's pipeline is the loop `investigation`; a stage of one loop may run another loop as a child case; every loop says where each stage's components come from, and a run records exactly what it ran with. Part B adds a builder conversation that reads the catalogue, proposes manifest changes a person accepts one file at a time, and probes sources through `runQuery`, all in a ledger of its own.

**Architecture:** `src/pipeline/loops.ts` reads `kind: loop` manifests into a `LoopCatalog`. A resolved loop is a `Pipeline` (as today), a `Profile`, a `Components` reader and a `LoopLock`: the list of every manifest the loop uses, by kind, id, source and sha256. The bytes of every loaded manifest go into the content store (`<data>/blobs`, the workbench chain's `BlobStore`, where a blob's name is the manifest hash the registry already records). A run that starts writes `loop.bound` (with the lock as a blob) and `run.started`; the engine afterwards builds that run's pipeline from the lock, so an edit to the root does not reach it. A stage with `runs: loop` is run by `subloopRunner`, which makes a child case through a host-supplied `ChildCases`, records `subloop.started` and `subloop.finished` in the parent, and pauses the parent while the child waits for a person. A loop file is a gzipped tar with `loop.json` (the lock, plus file hashes) first, read and written with the tar code slice 11 made. A builder session is a `CaseSession` under `<data>/builders/BUILD-N/`, with seven agent tools that write nothing outside it.

**Tech Stack:** Bun 1.3.14, TypeScript 7 (strict), `bun test`, happy-dom and headless Chromium for interface tests. `pivot` v0.2.0 (its `Registry` is not changed). No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-27-slice-12-loops-design.md` ("the design"; the owner's direction, parts A and B; the controller commits it from the scratchpad before Task 1). Branch `slice-12-loops` in the worktree `<repo>`, stacked on `slice-11-cases` once its Task 10 is committed. Decisions the design left open are the "Ruling:" lines in `.superpowers/sdd/2026-11-27-slice-12-loops/rulings.md`; where a task states one, it is the requirement.

**Part A is Tasks 1 to 14. Part B is Tasks 15 to 19 and starts when Task 14 is committed.**

## Global Constraints

- **The record decides.** Which loop a case is for, which version a run started with, which child a stage made and what came back are read from folded entries. Nothing is decided by looking at the root as it is now, except the version a *new* run binds.
- **Only a person passes a gate, in parent or child.** No code path in this slice writes `gate.passed`, `plan.accepted` or `product.published` for a child. The one resume code may write is `Engine.childSettled`, which lifts only a pause whose hold is `{ kind: "child" }` and passes no gate.
- **Only a person writes a manifest.** `saveManifests` (the one function that writes into a root) takes an actor and refuses any that is not `{ kind: "human" }`. No file under `src/agents/` imports `src/modules/loop-write.ts`, `src/modules/loop-import.ts`, `src/core/loopfile.ts` or `node:fs`'s write functions. The server names the actor; no route takes one.
- **One custody point.** Every query, a child's and a probe's alike, goes through `runQuery` (`src/modules/runner.ts`), which is not changed. A child's queries are in the child's ledger; a probe's are in the builder session's ledger.
- **The fold never throws and never mutates its input.** Every new payload field is optional or belongs to a new entry type. A malformed payload is recorded in `skipped`. The fold skips `subloop.child`, `subloop.started`, `subloop.finished` and `loop.bound` from an actor of kind `agent`, and `builder.decided` and `builder.probe_decided` from any actor that is not `human`.
- **Old ledgers fold unchanged and replay stays exact.** No existing payload gains a required field. Every existing field of `fold(entries, n)` for a ledger written before this slice is what it was. `fold(entries, n)` equals the live state after entry `n` for new ledgers too: everything new is state derived by `apply` from entries in the hash chain. A parent's fold reads no other ledger.
- **No secret is read, written, exported or shown.** A credential is named by reference (`credential: <name>` on a source, granted to a root by the configuration's `roots[].credentials`); its value is set outside the workbench. An export holds no `location`, `credential`, `user` or `tls_verify` of a source, no `model` manifest, no `script` manifest, no configuration, no case data. Every byte that would be exported, proposed or shown to the builder's model is searched for each secret value the workbench holds (`Secrets`), and a hit refuses the act.
- **A loop file is untrusted input.** Nothing from one is written anywhere before every member's name, kind, size and hash has been checked against `loop.json`. What it holds lands in a root that is not trusted.
- **Browser-safe core.** `src/core/state/**` imports nothing outside `src/core/`; no `Bun`, `process`, `Buffer`, `node:*`. `src/web/**` imports only `src/web`, `src/core/state`, `src/core/wire.ts`, `src/core/types.ts`, `src/core/canonical.ts`. `src/core/tar.ts` and `src/core/loopfile.ts` are server-side core, never imported by `src/web` or `src/core/state`.
- **No HTML sink, no inline style.** Elements are made only by `h` and `s`. A loop's title, its about text, a stage title, a manifest path and a diff line are text nodes or the value of a fixed attribute.
- **Loopback only.** Every new route is in `src/server/app.ts`'s route table, behind `refusal()` (Host, Origin, JSON) and the role check.
- **Exact values:** the default loop id is `"investigation"`; the configuration's `loops` block is `{ default: "investigation", max_depth: 2, max_children: 8, store: "<data_dir>/loops", imports: "<data_dir>/imported" }`; a loop file is named `<loop-id>.v<version>.<first 12 hex of its pipeline hash>.loop.tar.gz`; `loop.json` is the first member; `LOOP_FILE_FORMAT` is `1`; `LOCK_FORMAT` is `1`; the largest loop file read is `16777216` bytes unpacked; `WORKBENCH_VERSION` is `"0.12.0"`; a builder session's id is `BUILD-N` and its folder `<data>/builders/BUILD-N/`.
- **Deterministic.** No `Math.random`, no `Date.now` in a fold, a hash or a builder of entries; `<` on strings, not `localeCompare`, in new code. A lock's items are sorted by `stage`, `kind`, `id` with `<`.
- **The real environment stays out of the repository.** Tests and the sample use synthetic data only: the sample's names, loopback and RFC 5737 addresses, `example.*` domains.
- **Tests:** `timeout 120 bun test <file>` while iterating; `timeout 900 bun test && timeout 300 bun run typecheck` before each commit, the full run with `WORKBENCH_REQUIRE_BROWSER=1`. No test asserts an absolute duration. Every test makes its files under a fresh `mkdtempSync` directory and removes it, closes what it opens, and asserts `state.skipped` is `[]` when it drives a session. Report real RED: the failing run of the new tests, made before the implementation exists.
- **No wait loops, nothing left running.** Never wait with a `pgrep`-based loop or an `until` loop on a log (other sessions on this machine run `bun test` too, so such a loop never ends). Run commands in the foreground with a time limit. Leave no background process behind.
- **Commits:** on `slice-12-loops`, never pushed; `git add` by explicit path (other tasks may have uncommitted work in the tree). Never `git checkout`, `switch`, `stash` or `reset`. End every commit message with the attribution lines your own harness reminder gives you.
- **Other trees are not yours.** Do not touch `<repo>`, `-s9`, `-s10`, `-s11` or `<lake>/`.
- **A test outside your task's Files that your change breaks:** fix it if no task running beside yours lists that file; otherwise report it and leave it.

| Workbench chain: `loop.recorded`, `loop.output`, `manifest.written` | Task 2, Task 6, Task 9 | code; `manifest.written` by a person | nothing (a case fold ignores them, as it ignores `module.loaded`) |

`key` is `` `${run}/${stage}/${attempt}` `` with the parent's run id.

- **Old ledgers fold unchanged.** An old ledger holds none of the new types and none of the new values. `state.loop` stays `{ id: null, pending: null, bound: null, parent: null, children: {}, child_count: 0 }`, `state.builder` stays `{ proposals: {}, probes: {} }`, the two new counters stay `0`, and every other field is what it was. `applyRun` is changed only where it validates the three widened unions.
- **Validated on fold.** `case.loop_set` after a `run.started` is skipped ("a case's loop is set before its first run"). `subloop.child` is read only while `state.seq <= 3` and no run has started. `subloop.finished` is read only for a key that `subloop.started` opened and that has no `finished`, and only when `child` is the one that key started; otherwise it is skipped with its reason. A `card.created` whose card has `from` is read only from an actor of kind `system`.
- **Replay stays exact.** A parent's state at `n` is `fold(parentEntries, n)`: the child's head and the hash of what came back are fields of `subloop.finished`, the returned cards are `card.created` entries of the parent's own chain, and the output is a blob of the parent. Replaying the parent never opens, folds or re-runs the child. The child replays on its own from its own ledger.
- **`verify` passes.** The new types are in `ENTRY_TYPES`. `BLOB_FIELDS` gains `"loop.bound": ["lock"]`, `"subloop.started": ["inputs"]`, `"subloop.finished": ["output"]`, `"builder.proposed": ["bundle"]`, `"loop.recorded": ["lock"]`, `"loop.output": ["value"]`, none nullable. `verifyLinks` (Task 7) adds a report beside `verifyCase`'s, it does not change it.

## How the hard questions are answered

**Today's pipeline becomes `loops/investigation.yaml`, and an old ledger's pipeline hash still matches.** Today `loadPipeline` takes every `stage` manifest and hashes `sha256Hex(canonical(stages.map((s) => [s.id, s.hash])))`, and `Engine.drive` pauses a running run whose `run.started.pipeline_hash` is not that. From this slice a resolved loop has two hashes. `legacy_hash` is that same formula over the loop's stages, in order, and exists when every stage is named by id and none runs a loop (else null). `hash` is the version-2 hash (below), which covers every component. A run that starts now writes `loop.bound` and records `hash`. A run with no `loop.bound` is from before this slice: the engine holds it to `legacy_hash` of the case's loop as the root has it, which for the sample (and any root whose stage manifests are unchanged) is the value the old ledger recorded. So an old running, waiting or paused run goes on exactly when it would have gone on before; the fold never read `pipeline` or `pipeline_hash`, so replay is untouched. `sample/loops/investigation.yaml` names the nine stages by id and `profile: investigation`. A root with stage manifests and no loop manifest at all gets the *implicit* loop `investigation`: every stage manifest, profile `investigation`, as `loadPipeline` did. Task 3 pins the sample's legacy hash as a literal computed on the tree before any change.

**The version-2 pipeline hash, and where components come from.** A loop's `components` block names a source for a component of a stage; a component it does not name comes from `root` (omitted is inherited). A stage's components are: its `profile` entry's `persona`, `procedure`, `skills`, `references`, `gates`; the profile's `rules`, `framework`, `standard` and the profile manifest itself (stage `"*"`); the stage's `schema`; and for a stage of role `checks`, every `check` manifest and every check's script file. Sources:

| Source | Resolves to | Refused when |
|---|---|---|
| `root` | the registry's manifest of that kind and id, from a trusted root | it is not loaded, or its root is not trusted |
| `{ pinned: <sha256> }` | the content store's bytes of that hash, parsed as a manifest | the workbench chain has no `module.loaded` of that hash with this kind and id from a root the configuration trusts now; the bytes are missing or do not parse |
| `{ loop-output: "<loop>.<output>" }` | the value of the latest `loop.output` chain entry of that loop and output whose `outcome` is `published`, as a `reference` part marked with the product's marking | the component's kind is not `reference`; there is no such entry |
| `{ memory: "<store>/<selector>" }` | nothing | always: "memory sources arrive in slice 13" |

`hash = sha256Hex(canonical({ v: 2, loop: id, manifest: <the loop manifest's hash>, entry, stages: [[id, hash], …], components: [[stage, kind, id, source, hash], …], subloops: [[stage, loop, <that loop's hash>], …] }))`, components sorted by stage, kind, id. An inline stage's hash is `sha256Hex(canonical(body))`. Models, sources, pivots, playbooks and inventories are not components: a query already records `source_hash` and `pivot_hash`, a playbook run its `playbook_hash`, and a model request its model. The lock (`LoopLock`) is that same list with titles and root-relative paths; its canonical JSON is a blob in the content store and, for a bound run, in the case's own blob store.

**A running case keeps its version.** `loop.bound.lock` names the lock. `LoopCatalog.fromLock` rebuilds the pipeline, the profile and the component reader from content-store bytes by hash, never from the root. `Engine` binds at construction (`forCase`) and again in `start`. A bound run whose content is not in this workbench's content store (a case file loaded from another workbench) pauses: "this run's loop version is not in this workbench; import its loop file".

**A sub-loop child links both ways.** `subloopRunner` for stage `S`, attempt `a` of run `R` in parent `P`:
1. Reads `state.loop.children["R/S/a"]`. With `finished` set it returns the recorded pass or fail and writes nothing.
2. With nothing recorded: checks the caps; builds the child's inputs from the parent's state (`inputsOf`), `input_hash = sha256Hex(canonical(inputs))`; asks `ChildCases.find(link)` for a child a stopped process already made for this link, else `ChildCases.create`, which commits `case.created`, `case.loop_set` and `subloop.child` (and one `card.created` per input card) in one commit of the child's ledger; then commits `subloop.started` in the parent with the inputs as a blob.
3. Calls `ChildCases.drive(child)`: the child's run is started if it has none and carried as far as it goes without a person.
4. Child `finished`: computes `outputsOf(childState, loop.outputs)`, `output_hash = sha256Hex(canonical(outputs))`, and commits `subloop.finished` together with the returned cards and proposals. A child that finished `stopped` fails the stage with the child's reason. Otherwise the stage passes.
5. Child waiting, paused or interrupted: returns `{ kind: "waiting_child" }`; the engine commits `run.paused` with reason `waiting on child CASE-N: <why>` and hold `{ kind: "child", stage, child }`. When the child's drive next settles the host calls `Engine.childSettled(child)` on the parent, which writes `run.resumed` by the engine and advances; the runner looks again. A person's own resume does the same.
The child's ledger names the parent (`subloop.child`); the parent's names the child (`subloop.started`). A stop between the two commits leaves a child that names a parent which does not name it; step 2's `find` adopts it. A child's marking is `strictest(parent's case marking, each input card's marking)`. Returned cards keep their own marking.

**Depth and count caps.** `loops.max_depth` (default 2) is the most levels below a case that no case started: a child has `depth = parent.depth + 1`, and a stage that would make a child at `depth > max_depth` pauses the run ("sub-loop depth cap of 2 reached"). `loops.max_children` (default 8) is the most `subloop.started` entries one case may hold; past it the run pauses ("this case has started 8 sub-loops, the cap"). Both are also checked when a loop is validated: the chain of `runs: loop` references from a loop may be at most `max_depth` long, and a loop that reaches itself is refused whatever the cap.

**A loop file.** `exportLoop` writes `loop.json` first, then `manifests/<root-relative path>` for the loop manifest and every item of the lock (and of each sub-loop's lock), then what the loop's `uses` block names: playbooks, the pivot files that hold a named pivot, and each named source (and each source a named pivot uses) as a *shape*: `location` replaced by `"unset"`, `credential`, `user` and `tls_verify` removed, `confirmed: false`. `loop.json` is `{ format, workbench, loop, version, title, about, hash, legacy_hash, lock, subloops: LoopLock[], files: [{ path, kind, id, sha256, bytes, origin: sha256 | null }] }`; `origin` is the hash of the manifest as it is in the exporting root when the exported bytes differ (a source shape). `importLoop` reads the file twice, as slice 11's `checkCaseFile` and `extractCaseFile` do: the first pass writes nothing and refuses a first member that is not `loop.json`, any member that is not a regular file, a name outside `manifests/` or with a `..`, an absolute or empty segment, a member the list does not have or a listed one that is missing, a size or hash that differs, and more than 16 MiB. Then, for each file's `(kind, id)`: one the registry holds with the same hash is left out; one it holds with another hash refuses the whole import, naming it; the rest are written with the `wx` flag under `<loops.imports>/<loop-id>-<12 hex>/`. Every folder of `loops.imports` is a root that is not trusted unless the configuration's `roots` lists it. So an imported `loop`, `stage`, `persona`, `check` and every other trusted-only kind is refused by the registry, with its reason on the Loops page, until the person trusts the root (`trust_root`, which writes the configuration).

**Part B's builder.** Seven tools, all in `src/agents/tools/builder.ts`, none in a stage's list: read (`loop_catalogue`, `adapter_catalogue`, `list_connectors`, `list_roots`, `validate_manifest`), propose (`propose_change`) and probe (`request_probe`). `propose_change` takes files as `{ path, text }` under the write root, runs `checkChange` (the function a save runs: a candidate copy of the root's manifests with the files laid over it, loaded with `loadRegistry` and `loadLoops`) and records `builder.proposed` only when it passes; a proposal that does not pass is the tool's error, with the problems, and the person never sees it. A person's `decide` on one file re-runs `checkChange` on the root with that one file laid over it, writes it with `saveManifests` as the person, and records `builder.decided` and, on the workbench chain, `manifest.written`. `request_probe` records `builder.probe_asked` and returns at once; a person's approval runs it with `runQuery` (or `runPivot`, which calls it) in the builder session, in the person's name, and the result is a card of that session. The session's marking is `strictest(its starting marking, every card's marking)` and is the `case_marking` of every pack sent to the builder's model.
