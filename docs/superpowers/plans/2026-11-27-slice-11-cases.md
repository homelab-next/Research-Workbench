# Cases Load and Unload, with a Case Store (slice 11) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A case can be put away as one verifiable file in a case store and brought back exactly as it was. The person unloads, loads, lists, searches and deletes from the interface and the command line, and may tick "unload after publishing" at the publish gate.

**Architecture:** A case file is a gzipped tar of the case folder with `case.json` first (`src/core/casefile.ts`, no dependency). The store is a folder of such files (`src/core/store.ts`). `Workbench.unloadCase` and `Workbench.loadCase` move a case between `<data>/cases/` and the store; each has one atomic commit point, a rename of the case folder. Three new entry types (`case.unloaded`, `case.unload_failed`, `case.loaded`) and one optional field on `gate.passed` (`unload_after`) are folded by a new reducer, `applyArchive`, into one new state field (`archive`). The server's hub releases a case's engine and streams before unloading it and unloads after a published run when the person ticked the box; the browser gets a Case store view, an Unload menu item, a setting and a checkbox at the gate.

**Tech Stack:** Bun 1.3.14, TypeScript 7 (strict), `bun test`, happy-dom and headless Chromium for interface tests. `node:zlib` streams for gzip; the tar reader and writer are ours. No new dependency.

**Spec:** [`docs/superpowers/specs/2026-11-27-slice-11-cases-design.md`](../specs/2026-11-27-slice-11-cases-design.md) ("the design"). Branch `slice-11-cases`, stacked on `slice-10-person-ux` `7d858d9`. Decisions the design left open, and the owner's ruling on the on-complete checkbox, are the "Ruling:" lines in `.superpowers/sdd/2026-11-27-slice-11-cases/progress.md`; where a task states one, it is the requirement.

## Global Constraints

- **The record decides.** Whether a case is to be unloaded after publishing, whether an unload failed, and what a case was loaded from come from the folded entries. The global setting is only the default of a checkbox.
- **Only a person or code unloads, loads or deletes.** No agent tool and no stage runner calls `unloadCase`, `loadCase` or the store's `delete`. The fold skips `case.unloaded`, `case.unload_failed` and `case.loaded` from an actor of kind `agent`, and reads `unload_after` only on a person's `gate.passed`. The server names the actor; no route takes one.
- **No gate is passed here.** The gate checkbox sends nothing when it is ticked. Only `approve` writes `gate.passed`, as before.
- **The fold never throws and never mutates its input.** Every new payload field is optional or belongs to a new entry type. A malformed payload is recorded in `skipped`.
- **A case is loaded exactly when `<data>/cases/CASE-N/` exists.** Unload and load each change that with one `renameSync`. Everything before the rename can fail or stop and leave the case where it was.
- **Nothing is stripped.** A case file holds every regular file of the case folder. A folder that holds a link or a special file is not packed: the unload fails and says which.
- **An archive is untrusted input.** Nothing from a case file is written into the working set before every member's name, kind, size and hash has been checked against `case.json`, and nothing becomes a loaded case before `verifyCase` passes on what was extracted.
- **Browser-safe core.** `src/core/state/**` imports nothing outside `src/core/`; no `Bun`, `process`, `Buffer`, `node:*`. `src/web/**` imports only `src/web`, `src/core/state`, `src/core/wire.ts`, `src/core/types.ts`, `src/core/canonical.ts`. `src/core/casefile.ts` and `src/core/store.ts` are server-side core (like `workbench.ts`) and are never imported by `src/web` or `src/core/state`.
- **No HTML sink, no inline style.** Elements are made only by `h` and `s`. A title, a question or a file name from a case file is a text node or the value of a fixed attribute.
- **Loopback only.** Every new route is in `src/server/app.ts`'s route table, behind `refusal()` (Host, Origin, JSON) and the role check, like every other.
- **Exact values:** file name `CASE-12.TLP-AMBER.tar.gz`; `case.json` is the first member; `CASE_FILE_FORMAT` is `1`; `WORKBENCH_VERSION` is `"0.11.0"`; the size cap is `cases.max_bytes`, default `2147483648`; the store is `cases.store`, default `<data_dir>/store`; `cases.on_complete` is `"keep"` (default) or `"unload"`; the mark file is `<data>/cases/.high-water`; the delete log is `<store>/deleted.log`.
- **Deterministic.** No `Math.random`, no `Date.now` in a fold or a builder; `<` on strings, not `localeCompare`, in new code. Times in a manifest are entry timestamps or come from the workbench's `now`.
- **The real environment stays out of the repository.** Tests use synthetic cases only: the sample's names, loopback and RFC 5737 addresses, `example.*` domains.
- **Tests:** `timeout 120 bun test <file>` while iterating; `timeout 900 bun test && timeout 300 bun run typecheck` before each commit, the full run with `WORKBENCH_REQUIRE_BROWSER=1`. No test asserts an absolute duration. Every test makes its files under a fresh `mkdtempSync` directory and removes it, closes what it opens, and asserts `state.skipped` is `[]` when it drives a session. Report real RED: the failing run of the new tests, made before the implementation exists.
- **No wait loops, nothing left running.** Never wait with a `pgrep`-based loop or an `until` loop on a log (other sessions on this machine run `bun test` too, so such a loop never ends). Run commands in the foreground. Leave no background process behind.
- **Commits:** on `slice-11-cases`, never pushed; `git add` by explicit path (other tasks may have uncommitted work in the tree). Never `git checkout`, `switch`, `stash` or `reset`. End every commit message with the attribution lines your own harness reminder gives you.
- **Other trees are not yours.** Do not touch the main checkout `<repo>`, the other slices' worktrees (`<repo>-s9`, `<repo>-s10`; a live server may run from one) or the lake folder `<lake>`.
- **A test outside your task's Files that your change breaks:** fix it if no task running beside yours lists that file; otherwise report it and leave it.

## The ledger: what is added, and why old ledgers and replay are unchanged

| Addition | Shape | Folded into |
|---|---|---|
| Entry `case.unloaded` | `{ store: string; head: { seq: number; hash: string } }`, by a person or code; `head` is the head before the entry | `state.archive.pending` |
| Entry `case.unload_failed` | `{ reason: string }`, by a person or code | `state.archive.failed`; clears `pending` |
| Entry `case.loaded` | `{ file: string; head: { seq; hash }; id: string; original_id: string \| null }`, by a person or code; `head` is the head before the entry | `state.archive.loaded`; clears `pending` and `failed` |
| Field `unload_after?: boolean` on `gate.passed` | read only on a person's pass of the `publish` gate | `state.archive.unload_after` |

- **Old ledgers fold unchanged.** No existing payload gains a required field. An old ledger holds none of the three types and no `unload_after`, so `archive` stays `{ pending: null, failed: null, loaded: null, unload_after: false, unloads: 0, loads: 0 }` and every other field is what it was. `applyRun`'s handling of `gate.passed` is not touched.
- **Validated on fold.** `case.unloaded` and `case.loaded` must name the head before them: `payload.head.seq === entry.seq - 1` and `payload.head.hash === entry.prev_hash`. The entry carries its own `prev_hash`, so the fold checks this with no other input. One that does not is skipped with its reason.
- **Replay stays exact.** Everything new is state derived by `apply` from entries in the hash chain, so `fold(entries, n)` is the state the live session had after entry `n`, before and after a round trip through a file. A case file carries `ledger.sqlite` byte for byte (its sha256 is in `case.json`), so entries `1..head` of a loaded case are the rows that were unloaded; the only entry a load adds is `case.loaded`, appended through `Ledger` like any other. A paused or waiting run comes back paused or waiting because none of the three entries touches `state.run`.
- **`verify` passes.** The three types are in `ENTRY_TYPES`; none has a blob field, so `BLOB_FIELDS` and `BLOB_NULLABLE` are untouched. `verifyCase` reads the case id from the ledger's own `meta`, so a renumbered case verifies under the id its chain was made with.
- **Every entry's hash binds its case id** (`entryHash` hashes `case`). A case that is given a new id on load therefore keeps the id it was created with inside its ledger: `Entry.case` and `meta.case_id` stay the *chain id*. The new id is the folder's name, the session's `id`, the address in the interface and the id in new products. `case.loaded` records both.

## How the four hard questions are answered

**The id counter.** `Workbench.nextNumber()` is `1 + max(0, W, S, D, M)`: `W` the numbers of the folders in `<data>/cases/` that match `CASE-N`; `S` the numbers in the names of the store's files (`CASE-N.<marking>.tar.gz`); `D` the ids in `<store>/deleted.log`; `M` the number in `<data>/cases/.high-water`. `M` is written (temporary file, fsync, rename) before `createCase` makes a folder, before a load's folder is renamed into place, and before an unload's folder is renamed out, and it never goes down. So an id is not reused after its case was unloaded to the store (`S`), unloaded elsewhere with `--to` (`M`), deleted from the store (`D`, `M`), or while the store cannot be read (`M`; the unreadable store is reported through `onError` and does not stop `createCase`). Names are read with `readdirSync`; no file is unpacked.

**A crash in the middle of an unload.** The order is: (1) commit `case.unloaded`; (2) close the session; (3) write `<store>/.tmp-<id>-<pid>-<uuid>.part` and fsync it; (4) read it back with `checkCaseFile` and compare its manifest with the one written; (5) rename it to its name and fsync the store; (6) write the mark; (7) rename `<data>/cases/CASE-N` to `<data>/cases/.unloading-CASE-N-<uuid>` and fsync `cases/`; (8) remove that folder. Step 7 is the commit point. A stop before it leaves `cases/CASE-N` whole, so the case is loaded; the next `session(id)` finds `archive.pending` set on a case that is in the working set and writes `case.unload_failed` ("the workbench stopped before the case was unloaded"). If the stop came after step 5, the store also holds a valid file one entry behind; loading it is refused ("already loaded") and the next unload replaces it. A stop after step 7 leaves the case unloaded and a `.unloading-*` folder, which `Workbench.open` removes. A failure (not a stop) at steps 2 to 7 removes the temporary file, reopens the session and writes `case.unload_failed` with the reason.

**Load refuses traversal, links and oversize.** `checkCaseFile` reads the archive once and writes nothing. It refuses: a first member that is not `case.json`; a `case.json` that is not a manifest; a member whose type flag is not a regular file (so a hard link, a symbolic link, a directory, a device, a pax or GNU extension header are all refused by kind); a name that is absolute, holds `\`, a NUL, or a segment that is empty, `.` or `..`, or is longer than the header's name fields; a name twice; a member the manifest does not list, or a listed one that is missing; a size or sha256 that differs; and a running total over `max_bytes`, checked from each header before its body is read and again on the bytes that come out of gzip. `extractCaseFile` runs the same reader, writes each member with the `wx` flag under a new directory after checking the resolved path is inside it, and removes the directory on any failure.

**A loaded case's verify and replay.** After extraction to `<data>/cases/.loading-<uuid>/`, `loadCase` runs `verifyCase` on it and requires `ok`, `report.head === manifest.head.hash`, `report.entries === manifest.entries`, `report.case === manifest.chain` and entry 1's hash equal to `manifest.origin`. Only then is `case.loaded` appended and the folder renamed into `cases/`. Task 4's tests fold every prefix of a round-tripped ledger against the states captured live; Task 10 runs the `verify` command on a loaded case and replays it in the interface.

## Review Focus

Inputs the design implies and a person will meet, most likely first. Each has its test in the task named.

1. **The person unloads a case that another tab has open.** That tab's stream ends, its reconnect is answered 404, and it says the case was unloaded and goes to the list; it does not spin on "reconnecting". *Task 6 Step 5, Task 8 Step 5.*
2. **The store is on a share that is not mounted, or is full.** Unload fails before or during the write, the case stays loaded, the list shows the failure with its reason, and the ledger holds `case.unload_failed`. A new case still gets a fresh id. *Task 4 Steps 5 and 1.*
3. **A case file from someone else with an id this workbench uses.** It is loaded under the next free id, its ledger still verifies, its entries still say the id it was made with, and the list shows both. *Task 4 Step 9.*
4. **A hand-made or damaged archive:** a symlink member, `../../etc/x`, an absolute name, a file edited after packing, a truncated ledger whose `case.json` was re-hashed, a 3 GB member. Each is refused with its reason and `cases/` holds nothing new. *Task 2 Steps 5 and 9, Task 4 Step 9.*
5. **The box is ticked, the run publishes, and the unload fails.** The case stays loaded with its product; nothing retries in a loop; ticking and approving a later run tries again. *Task 6 Step 7.*
6. **A title or a question in `case.json` that looks like markup, and a file name with odd characters.** Drawn as text; a file name outside the plain-name pattern is refused by the server. *Task 8 Step 1, Task 6 Step 3.*
7. **Delete with the wrong id typed, or by a hand-made request with none.** Refused by the server; the file stays; nothing is logged. *Task 6 Step 3.*

// src/core/casefile.ts — imports node:fs, node:zlib, node:path, node:stream, ./refused, ./hash, ./canonical, ./state/guards, ./types (types only). Not ./workbench.
export const WORKBENCH_VERSION = "0.11.0";
export const CASE_FILE_FORMAT = 1;
export const DEFAULT_MAX_CASE_BYTES = 2147483648;
/** A case file that cannot be made, read or trusted. `reasons[0]` says why, in words a person can act on. */
export class CaseFileError extends Refused {}
export interface CaseFileEntry { path: string; sha256: string; bytes: number }
export interface CaseManifest {
  format: 1;
  /** The id the case has on the workbench that packed it. */
  id: string;
  /** The id its ledger was made with: `Entry.case` of every entry. */
  chain: string;
  /** The hash of entry 1: the same in every copy of this case, whatever id it is given. */
  origin: string;
  title: string; asked: string; marking: Marking; starting: Observable[];
  status: string; outcome: "published" | "stopped" | null;
  published: { n: number; draft_hash: string }[];
  head: { seq: number; hash: string }; entries: number;
  workbench: string; unloaded_ts: string;
  /** Every file of the case folder but case.json itself, sorted by path with `<`. */
  files: CaseFileEntry[];
}
export type ManifestHeader = Omit<CaseManifest, "format" | "workbench" | "files">;
export const isCaseManifest: (x: unknown) => x is CaseManifest;
/** "CASE-12" + "TLP:AMBER" → "CASE-12.TLP-AMBER.tar.gz": every character of the marking outside [A-Za-z0-9+_-] becomes "-". */
export function caseFileName(id: string, marking: string): string;
/** The id and the marking part of a case file's name; null when it is not one. */
