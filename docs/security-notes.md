# Security notes: the server and the interface

What this slice relies on, and what it does not do. Each claim below has a test; the file named after it is where to look. Nothing here is a promise about a network, a second person or a machine you do not trust: this is one person on one machine.

## What the server guarantees

- **It answers only on `127.0.0.1`, and only to its own origin.** The socket is bound to `127.0.0.1` and no other address (`tests/server/boundaries.test.ts`, which also allows `Bun.serve` nowhere but `src/server/app.ts`). A request must carry `Host: 127.0.0.1:<port>` exactly; `localhost:<port>` is refused with a line naming the right address, so there is one origin to reason about. An `Origin` that is not the server's own, a `Sec-Fetch-Site` of `cross-site`, a `POST` with no `Origin` or not `application/json`, any method other than `GET` and `POST`, and a body over 1 MiB are all refused before a handler runs. No `Access-Control-*` header is ever sent, on an answer, a refusal, an error or the entry stream, and every response carries `X-Content-Type-Options: nosniff`. (`tests/server/guard.test.ts`, `tests/server/boundaries.test.ts`.)
- **There is no sign-in.** One person, one machine. Whoever can open a connection to `127.0.0.1` on this machine is that person. The server names the actor itself (`{ kind: "human", id: <configured user> }`), and a request body that names an actor is refused.
- **Roles are checked on the server, and there is one configured role.** Every read and every command is checked against `config.role` before it runs, so hiding a control in the page is never the only check. The role comes from the configuration file, not from the request: nothing in a request can raise it. A requester or leader view may read the page and little else. (`tests/server/guard.test.ts`, `tests/server/commands.test.ts`, `tests/server/boundaries.test.ts`.)
- **A command writes entries and returns.** It never advances the run on its own; only the commands the pipeline contract names do, and for no other. A `GET` never writes an entry.
- **After a stop, nothing new starts.** Once the person stops (or pauses) a run, no model reply runs a tool call, no plan budget is spent, and no proposal is accepted in the person's name. A query already issued to a source before the stop is not cut off: it records its result and its card, so the ledger says what the source was asked and what it answered. (`tests/server/plan-commands.test.ts`, `tests/agents/loop.test.ts`.)
- **The `http`, `trino` and local-model connections refuse the server's own address.** `serve` hands the server's `host:port` to the connector pool and to the model providers. A source or model endpoint whose location is that port, under any loopback name (`127.0.0.1`, `localhost`, `[::1]`, and the spellings the URL parser reads as those: `127.1`, `0x7f000001`, `2130706433`, the IPv6 long form `[0:0:0:0:0:0:0:1]`; and, by the check itself, a trailing dot such as `localhost.` and the IPv4-mapped `[::ffff:127.0.0.1]`), is refused when it is built and again before each request, because the port may not be known until the server is listening. Another address on `127.0.0.0/8` is not treated as this server. (`tests/modules/own-server.test.ts` for the model providers and pivot's `tests/connectors/own-server.test.ts` for the connectors, `tests/cli/serve.test.ts`, which starts `serve` and watches a query to such a source be refused.)
- **The sample fixture is a separate listener, for the sample only.** `serve --sample-fixture [port]` also starts a small reputation service on `127.0.0.1:<port>` (4801 by default) that answers the sample source and nothing else. It is a second loopback listener with none of the server's checks; it serves the sample's invented data and holds no case. It is started only after the workbench lock is held, and stopped with the server. Without the flag it does not run.
- **Every query the workbench sends is `runQuery`'s.** The catalogue, the query guard, the connectors, the route search and the route walker come from pivot (`github:homelab-next/pivot#v0.1.0`, pinned in `bun.lock` by the hash of the annotated tag object, which names exactly one commit). The workbench does not use pivot's run endpoint or log; every query it sends is `runQuery`'s. pivot's walker is handed an executor that calls `runPivot`, so a route's lookups are in the ledger like any other. Nothing under `src/` imports pivot's `run` or `service` code, names `runLogged`, `RunLog` or `startService`, or calls a connector's `run` or `estimate` outside `src/modules/runner.ts` (also as `c["run"](…)` or through `.call`, `.apply` or `.bind`; a call on a connector held under a name like `stmt` is not caught by this line scan), and no pivot module the workbench loads is under `run/` or `service/`. (`tests/repo/pivot-seam.test.ts`, `tests/modules/custody.test.ts`.)
- **The ledger's hashes are the workbench's own.** The chain (every entry hash, and `verify`) and every digest the workbench records or compares with a recorded one are computed by `src/core/canonical.ts` and `hash.ts`, the workbench's copies: a result's `rows_hash` (`rowsHash` in `src/modules/runner.ts`, which reuse and revalidation compare again), the does-it-belong playbook's hash (`src/modules/belongs.ts`), the plan pins and the blob hashes. The manifest hashes (`module.loaded`, a query's `source_hash` and `pivot_hash`, the playbook and inventory hashes) are of the file's bytes, and pivot's registry computes them first; `loadRegistry` then hashes each file again with the workbench's own `sha256Hex` and refuses the load, recording nothing, if any differs (a file changed while loading differs too). So a later pivot whose hashing changed could not change what a recorded hash means: it would stop the load, and it would fail the parity test. `tests/repo/pivot-seam.test.ts` fails if `src/` takes `canonical`, `sha256Hex`, `rowsHash`, `entryHash`, `GENESIS` or `belongsPlaybook` from pivot (but for the one wrapper), imports pivot's `base/` copies, or loads a registry anywhere but `loadRegistry`; and it holds pivot's and the workbench's canonical, hash, schema, `rowsHash` and does-it-belong hash equal on a varied set of inputs. (`tests/repo/pivot-seam.test.ts`, `tests/modules/registry.test.ts`.)
- **A playbook reaches a source only through the runner.** A playbook never calls a connector. Every lookup is `runPivot` / `runQuery`, so it is a `query.issued` and a `query.result` (or `query.failed`) linked to the playbook's job, with purpose `playbook`, and a card that names the query. The steps are `playbook.started` (the playbook, its manifest hash, the inputs, the window, every step's pivot hash) and `playbook.step` and `playbook.finished`. A reused lookup sends nothing and names the query and card it reuses. A playbook never spends a budget, passes a gate, keeps a card or accepts a proposal, and its actor is the person or `system: playbook`, never an agent. (`tests/modules/playbook-run.test.ts`, and `tests/sample/playbook-custody.test.ts`, which runs a playbook and a "does it belong?" and checks that every card traces to its query, its result and its bytes, that the chain verifies and that replay equals the live state.)
- **Playbooks and inventories load only from trusted roots.** A `playbook` or `inventory` manifest from an untrusted root is rejected with the reason, as a pivot is, so steps and completeness claims are not taken from text no one vouched for. (pivot's `tests/catalogue/playbooks.test.ts`, `tests/catalogue/inventories.test.ts` and `tests/catalogue/trusted-only.test.ts`, which holds pivot's default list to every kind the workbench keeps to trusted roots; the workbench passes its own list as well, in `src/modules/registry-record.ts`, and `tests/modules/registry.test.ts` pins that list and checks that it alone refuses all seventeen kinds were pivot's default only `playbook` and `inventory`.) Since pivot v0.1.0 such a manifest is refused before its body is checked, so an invalid one is reported as accepted only from a trusted root rather than with a schema error, and the reserved-id message is worded differently. A `module.rejected` is recorded once for each distinct error, so the first load after the upgrade appends one fresh `module.rejected` for each file affected; that is expected and harmless.

- **Only a person's entries carry a person's authority.** The fold accepts `finding.overruled`, `question.answered`, `review.ruled` and a card that carries `person` (a statement) only from an actor of kind `human`, and `question.asked` only from an agent; anything else is recorded in `skipped` and changes nothing. The server names that actor itself, so no command can make a model's text a person's statement or a person's overrule. No command or tool for statements, questions or overrules writes `gate.passed`. (`tests/core/state-person.test.ts`, `tests/core/state-cards.test.ts`, `tests/sample/person-acceptance.test.ts`.)
- **A question is model text, and keeps its request's marking.** The text of a question a stage asked enters a later pack only with its `question.asked` entry as what wrote it, so it is as strict as the model request that wrote it. An answer card is at least as strict as the case, as the marking the person chose and as that request; an answer marked below the case's marking is refused, and an answer to a question whose request cannot be found is marked `TLP:RED`. (`tests/pipeline/questions.test.ts`, `tests/server/question-commands.test.ts`.)

## Cases: the case file and the case store

- **A case file is the whole case, unredacted, and says its marking in its name.** It holds every regular file of the case folder: the ledger, every blob (the rows and raw bytes each source returned, every model request and reply) and the published products. Nothing is stripped or redacted, so it is as sensitive as the case's strictest card; treat the store folder (`cases.store`) and every folder you unload to with `--to` as you treat the data folder. The file is named `CASE-12.TLP-AMBER.tar.gz`, after the case's marking, and `case.json` carries the marking too. It never holds a credential's value: none is ever written to a ledger or blob (see "What reaches the browser"), and `case.json` names no local path; the reason of a failed unload has the store's and data folder's paths replaced by their names. A case folder that holds a link or a special file is not packed: the unload fails and names it. (`tests/core/casefile.test.ts`, `tests/core/workbench-cases.test.ts`.)
- **A case file is untrusted input, and a load writes nothing until it has been checked.** The first pass reads the archive once and writes nothing at all. It refuses, in this order as it reads: a file that is not gzip or not ustar; a first member that is not `case.json`; a `case.json` that is not a case manifest; any member whose kind is not a regular file (a hard or symbolic link, a directory, a device, a FIFO, a pax or GNU extension header are refused by kind); a name that is absolute, holds `\` or a NUL, has an empty, `.` or `..` segment, or is too long for the header; a name that appears twice; a member `case.json` does not list; a size or a sha256 that differs from `case.json`; a listed file that is missing; and a running total over `cases.max_bytes` (2 GiB by default), checked from each header before its body is read and again on the bytes that come out of gzip, so a small file that inflates is refused as it inflates. Then the id is checked: a case whose id is held here by another case, or by another file in the store, is refused, and the same case is refused as already loaded. Only then is it extracted, by the same reader, to a new folder `cases/.loading-<uuid>`, each file opened with `wx` after its resolved path is checked to be inside that folder; the chain is verified there, and the head, the entry count, the case id and the hash of entry 1 must be the ones `case.json` names. Any failure removes the folder; nothing is in the working set or any ledger. The case appears only by one rename into `cases/CASE-N`. (`tests/core/casefile.test.ts`, `tests/core/workbench-cases.test.ts`, `tests/sample/cases-acceptance.test.ts`.)
- **Delete is checked on the server.** Deleting a file from the store takes the case's id typed by the person; the server reads the file's own `case.json` and deletes nothing unless the typed id is that file's case's. The route takes no actor (the server names the person), sits behind the same Host, Origin and JSON checks and the role check as every other, and writes a line to `<store>/deleted.log` before the file is removed. It never touches a loaded case. (`tests/server/cases.test.ts`, `tests/server/guard.test.ts`, `tests/sample/cases-acceptance.test.ts`.)
- **No agent can unload, load or delete a case.** The routes (`POST /api/cases/:id/unload`, `GET /api/store`, `POST /api/store/load`, `POST /api/store/delete`, `POST /api/settings`) are a person's, checked for the role and the origin like every command; no agent tool, stage runner or file under `src/agents/` or `src/pipeline/` names them or `unloadCase`, `loadCase` or the store, and no tool manifest of the sample does. The fold skips `case.unloaded`, `case.unload_failed` and `case.loaded` from an agent, and reads "unload after publishing" only from a person's pass of the publish gate; the unload after publishing is done by the workbench itself, as `system: workbench`. The case file and the store are never imported by the browser's code or by the fold. (`tests/server/boundaries.test.ts`, `tests/core/state-archive.test.ts`.)
- **A stop never loses a case.** An unload records `case.unloaded`, writes the file under a temporary name, reads it back against `case.json`, puts it in place, and only then takes the folder out of the working set with one rename. A stop or failure before that rename leaves the case loaded and records `case.unload_failed`; an id is never given twice, even while the store is unplugged. (`tests/sample/cases-acceptance.test.ts`, which stops a real process in the middle of an unload.)

## What the page guarantees

- **The page is a constant.** It is a fixed document that loads exactly one script (`/app.js`) and one stylesheet (`/app.css`) and nothing else; no data is ever written into it (`tests/server/boundaries.test.ts` counts them). It runs under `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'; trusted-types 'none'`. There is no inline script, no inline style and no `unsafe-*` source. (`tests/web/browser-run.test.ts` checks, in a real browser, that the page has none, that `document.body.innerHTML = ...` throws a `TypeError`, that every request the page made went to its own origin, and that the browser reported no script exception, console error or policy violation.)
- **The page builds no HTML from data.** Every element is made from a fixed list of tags and properties; text goes in as text; a link is made only for `https`, or for a blob or bundle of this server.
- **The injection lint is a guard and Trusted Types is the barrier.** `tests/web/lint.test.ts` fails the build if code under `src/web` uses an HTML sink, but a lint reads source and can be walked around by code it cannot see. What stops an HTML sink from working is the browser: `require-trusted-types-for 'script'` with `trusted-types 'none'` makes every such assignment throw, whatever the code looked like. Treat the lint as the early warning and the policy as the enforcement. The policy is only as good as the browser that enforces it.
- **Blobs and bundle files are attachments and never pages.** They are served with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and a media type that no browser runs: a blob as `application/json`, `text/plain` or `application/octet-stream`; a bundle file as `application/json` (`.json`), `text/markdown` (`.md`) or `application/octet-stream`. A blob recorded as `text/html` is served as bytes. `text/markdown` is not rendered by a browser, and with the attachment, nosniff and sandbox it is saved, never shown as a page of this origin. A path is never built from a request: a blob is found by its hash among the references an entry records, and a bundle file is read out of the bundle blob the `product.published` entry names, by a name the bundle's manifest lists. (`tests/server/evidence.test.ts`, `tests/server/boundaries.test.ts`.)

## What reaches the browser

- **Entries and blobs go to the browser exactly as recorded.** The browser folds the same entries the server does and must reach the same state, so an entry cannot be rewritten on the way. This is safe because entries and blobs hold no secret value by construction: a credential is named in a manifest, read from the environment when a query is sent, a response that echoes it is refused, and it is never written. A test plants a credential, runs a whole case to publication, and looks for the value and its name in every response: the page and its two files, every read, the entry stream, every blob and bundle file, the difference route, and the answers to `POST`s (creating a case, a command, a refused command, an unknown one, a lookup on the credentialled source with and without a budget, a verification) and to error responses. (`tests/server/boundaries.test.ts`, `tests/server/evidence.test.ts`.)
- **They may name where a source is.** A recorded query includes the text that was sent and the address it was sent to, and entries name the sources, models and accounts the case used. Anyone who can read a case can read these. If a location is itself sensitive, it should not be in a source's manifest.
- **Everything the server derives is a view with locations and credential names removed.** Source descriptions leave out `location`, `credential`, `user`, folders and roots; manifest problems carry paths relative to their module root; and text from a source error, a manifest problem or an unexpected exception goes through the same scrub before it is sent. Exactly what is scrubbed: the reference (every title and quality note), the agent's context view (titles and excerpts), the routes (titles), manifest problems, the reasons of every refusal (400 and 409) and of the bundle preview, and the line of a 500. Two derived views are not passed through the scrub, and why: the model list is built from model ids and fixed words only; the custody report is fixed words, counts and names relative to the case. The bundle preview's files are the bundle's own text, which comes from the ledger as a blob does, and are sent as recorded. (`tests/server/reads.test.ts`, `tests/server/boundaries.test.ts`.)
- **A blob that only a skipped entry refers to is still served.** The fold skips an entry whose payload is the wrong shape and records it in `skipped`. The server does not use the fold to decide what to serve: it serves any blob that an entry of the case names at a typed blob position, skipped or not. Such an entry is chained, its position is typed, and the browser already holds the raw entry, so nothing is disclosed that was not already sent. A hash that no entry names, a hash at a position that is not a blob field, and another case's blob are 404. (`tests/server/boundaries.test.ts`.)

- **The SVG builder is a fixed list.** Every SVG element of the Timeline and the Graph is made by `src/web/svg.ts` (pivot's `src/web/svg.ts`, re-exported), from a fixed set of tags and a fixed set of attributes. It writes no `style`, and there is no way for a caller to give it path data: a line is made from numbers it rounds itself, and text from the record is a text node. Nothing from data names a tag or an attribute. (pivot's `tests/web/svg.test.ts`, and `tests/web/lint.test.ts` here, which reads the pivot file the re-export names, covers that no other file makes SVG elements.)
- **`observed` is derived, bounded and as strict as its card.** It is computed from a result that is already in custody, in the commit that makes the card, and no source is contacted to make it. It holds at most 100 sightings of at most 24 points, and the fold refuses a card whose `observed` is over those limits or of the wrong shape. It is shown wherever its card is shown and carries the card's marking; it is not a separate copy of the data. (`tests/core/state-observed.test.ts`, `tests/sample/observed-acceptance.test.ts`.)

## What this does not do

- **Check programs are not confined to a folder.** The form checks of the pipeline run only from trusted roots, from a copy of the bytes that were hashed, with a stripped environment (no credential, only `PATH` and a locale) and a time limit that also ends what they start. They are not sandboxed: a program runs as the person who started the server and can read what that person can read. Do not mark a root as trusted unless you would run its programs. (`tests/pipeline/checks.test.ts`.)
- **A model on this machine must be at `127.0.0.1` or `[::1]`.** A model manifest that says `where: machine` is refused unless its host is one of those two numeric addresses; `localhost` is refused with a line saying to write `127.0.0.1`, so no resolver or hosts file can send prompts elsewhere. Nothing checks what is listening on that address: another program on this machine that holds the port would receive the prompts. A source (`http` or `trino`) may still name `localhost`, since it carries no prompt. (`tests/agents/providers.test.ts`.)
- **The route search can stop short without saying so.** pivot's route search stops after 20000 steps and does not report that it stopped, so a very dense catalogue can be offered fewer routes than exist, with no caveat. The routes it does offer are sound.
- **It does not defend against another person or process on this machine.** Any local process can connect to the port and, by setting the `Host` and `Origin` headers itself, act as the person. The checks protect against a web page in the person's browser, not against code running next to the server.
- **It does not use TLS and does not authenticate.** Traffic is on the loopback interface in the clear.
- **It does not stop hostile text in data.** Source data and model output are untrusted text. The interface shows them as text and the pipeline treats them as data, but rows returned by any source are still untrusted text, and a source from a trusted root can still say something misleading. What `list_sources` and `describe_source` now give a model for a source whose manifest came from an untrusted root is its id in place of its title (and each of its pivots' ids in place of their titles), no quality text and no quality notes, with `text_withheld: true`; table and column names (and the cost unit) of such a source are given only when they are plain identifiers (`[A-Za-z_][\w$.]{0,127}`). Not withheld: a source's id, which the model must name to use it. (`tests/agents/tools-sources.test.ts`.) Agents can only read and propose, so the worst outcome is a wasted query or a bad proposal, and both are in the ledger.
- **A playbook's values are source data.** Its steps are fixed text from a trusted root, but the values it follows from one step to the next are read from rows. A hostile value can cost up to `max_values` lookups a step and 50 a run, all of them free and all recorded; it cannot change a step, a pivot or the order.

- **What the lake guard is, and is not.** For a statement that names a guarded table, `checkGuardedShape` (`src/modules/sqlguard.ts`, which re-exports pivot's `src/guard/sqlguard.ts`; its tests are pivot's `tests/guard/sqlguard.test.ts`) refuses anything but one select whose where clause begins with the time column against the request's own two window literals; it also refuses `table (` (table functions), any `explain` but `explain (type ..., format ...)`, `limit all`, a limit above the source's `max_rows`, `offset`, and any control character (a carriage return ends a `--` comment in the engine, so the scanner does too). It is a text guard. It cannot catch a guarded table reached under another name: a view over it, a second catalog over the same storage, or table redirection. Unqualified names are caught only because the connector sends no catalog or schema header and `use` is refused. Whoever sets up the lake must not leave such a second name readable by the account the workbench uses.
- **Untrusted-root text is withheld on every route to a model.** Besides `list_sources` and `describe_source`: `find_routes` shows the pivot id as a hop's title; a card made from such a source is titled `result of <source id>`; `read_card` gives `quality note withheld: untrusted root` for its notes; and a product's `sources` carries `quality text withheld: untrusted root`. (`tests/agents/tools-sources.test.ts`, `tests/agents/draft.test.ts`.)
- **It does not limit the stream's memory use.** The entry stream has no backpressure limit; a reader that never reads can make the server hold its pending output.
